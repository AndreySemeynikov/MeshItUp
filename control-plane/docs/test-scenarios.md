# Сценарии тестирования канареечного релиза

## Контекст

Тестирование проводится на локальном Kubernetes-кластере (OrbStack) в namespace `mesh`. Цепочка вызовов: пользователь → API Gateway (Go) + sidecar → Inventory Service (Go) + sidecar. Control plane управляет маршрутизацией и жизненным циклом canary. Inventory Service поддерживает переменную окружения `FAULT_RATE` — процент запросов, возвращающих HTTP 500, что позволяет имитировать сбойную версию без изменения кода.

Параметры по умолчанию: начальный вес canary 10%, шаг увеличения 10%, порог ошибок 5%, интервал оценки 30 секунд, 3 последовательных успешных оценки для повышения веса.

Для всех сценариев предполагается непрерывный поток запросов через API Gateway (~2 запроса в секунду) для обеспечения evaluator'а метриками.

---

## Сценарий 1: Успешный канареечный релиз (полный цикл)

**Цель:** подтвердить, что стабильная новая версия сервиса проходит полный цикл канареечного релиза — от начального развёртывания до полного обновления всех подов.

**Параметры canary:**
- `canaryImage`: inventory-service:latest
- `canaryEnv`: VERSION=v2, FAULT_RATE=0, PORT=8080
- `initialWeight`: 10, `weightStep`: 10, `errorThreshold`: 5.0

**Шаги:**

1. Убедиться, что все запросы возвращают `version: v1`
2. Запустить canary через `POST /api/v1/canary/start`
3. Наблюдать появление canary-пода (`kubectl get pods -l version=canary`)
4. Проверить распределение трафика: ~90% v1, ~10% v2
5. Мониторить `GET /api/v1/canary/status` — наблюдать рост `currentWeight` (10→20→30→...→100)
6. Дождаться автоматического promote
7. Убедиться, что canary-под удалён, все запросы возвращают `version: v2`

**Ожидаемый результат:** статус `PROMOTED`, все поды обновлены до v2, canary Deployment и Service удалены. Время полного цикла ~13,5 минут (9 шагов × 90 секунд).

**Метрики для наблюдения в Grafana:**
- RPS по версиям: линия `canary` появляется и постепенно растёт, `stable` уменьшается
- Error Rate: обе версии около 0%
- После promote: одна линия `stable` на 100%

## Сценарий 2: Автоматический откат при высоком проценте ошибок

**Цель:** подтвердить, что система автоматически обнаруживает нездоровую версию и выполняет откат без вмешательства оператора.

**Параметры canary:**
- `canaryEnv`: VERSION=v2-faulty, FAULT_RATE=20, PORT=8080
- Остальное — по умолчанию

**Шаги:**

1. Запустить canary с FAULT_RATE=20 (20% запросов к canary вернут 500)
2. Дождаться первого цикла оценки evaluator'ом (~30–60 секунд)
3. Проверить `GET /api/v1/canary/status`

**Ожидаемый результат:** статус `ROLLED_BACK`, `lastEvaluationResult` содержит сообщение вида "ROLLBACK: canary error rate 20.00% > threshold 5.00%". Canary-под и Service удалены. Все маршруты восстановлены: stable=100%. Время до отката: 30–60 секунд от момента начала поступления метрик.

**Метрики в Grafana:**
- Error Rate: кратковременный всплеск линии `canary` до ~20%
- HTTP Status Codes: появление красных столбцов (500)
- После отката: все метрики возвращаются к нормальному состоянию

## Сценарий 3: Откат на промежуточном этапе продвижения

**Цель:** подтвердить корректность отката, когда ошибки возникают не сразу, а после нескольких успешных повышений веса. Имитирует ситуацию, когда проблема проявляется только под нагрузкой.

**Шаги:**

1. Запустить canary с FAULT_RATE=0 (здоровая версия)
2. Дождаться повышения веса до 30–40% (наблюдать через `GET /canary/status`)
3. Вручную пересоздать canary-деплоймент с FAULT_RATE=30, имитируя внезапное ухудшение (или использовать `kubectl set env` для изменения переменной на лету):
   ```bash
   kubectl -n mesh set env deployment/inventory-service-canary FAULT_RATE=30
   ```
4. Дождаться оценки evaluator'ом

**Ожидаемый результат:** автоматический откат с промежуточного веса. Маршруты возвращаются к stable=100% независимо от того, какой вес имел canary в момент обнаружения проблемы.

**Что демонстрирует:** система защищена на каждом этапе канареечного релиза, не только в начале.

## Сценарий 4: Ручное управление — принудительный promote

**Цель:** продемонстрировать возможность ручного вмешательства оператора — немедленное продвижение canary без ожидания полного автоматического цикла.

**Шаги:**

1. Запустить canary с FAULT_RATE=0
2. Дождаться нескольких успешных оценок (вес 20–30%)
3. Выполнить `POST /api/v1/canary/promote`
4. Проверить состояние кластера

**Ожидаемый результат:** немедленное обновление stable Deployment на canary-образ, удаление canary-ресурсов, маршруты stable=100%. Статус `PROMOTED`.

**Что демонстрирует:** оператор может ускорить процесс, если уверен в качестве новой версии, не дожидаясь ~13 минут автоматического цикла.

---

## Сценарий 5: Ручное управление — принудительный rollback

**Цель:** продемонстрировать возможность немедленного отката оператором, даже если автоматический evaluator ещё не обнаружил проблему (например, обнаружена бизнес-логическая ошибка, не влияющая на HTTP status codes).

**Шаги:**

1. Запустить canary с FAULT_RATE=0 (метрики выглядят нормально)
2. Обнаружить «бизнес-проблему» (например, неверные данные в ответе: version=v2 возвращает некорректный JSON)
3. Выполнить `POST /api/v1/canary/rollback`
4. Проверить состояние

**Ожидаемый результат:** немедленное удаление canary, восстановление маршрутов. Статус `ROLLED_BACK`.

**Что демонстрирует:** автоматика покрывает метрические аномалии (error rate, latency), но оператор сохраняет возможность отката по любой причине.

## Сценарий 6: Граничное значение error rate

**Цель:** исследовать поведение системы при значениях ошибок на границе порога (error rate ≈ errorThreshold).

**Шаги:**

1. Запустить canary с FAULT_RATE=4 (4% ошибок, порог 5%)
2. Наблюдать поведение evaluator'а в течение нескольких минут
3. Фиксировать значения `lastEvaluationResult` в каждом цикле

**Ожидаемый результат:** canary проходит оценки и постепенно продвигается, так как 4% < 5%. Система корректно обрабатывает значения вблизи порога.

**Вариация:** повторить с FAULT_RATE=6. Ожидается автоматический откат (6% > 5%).

**Что демонстрирует:** точность работы evaluator'а и предсказуемость пороговой логики. Важно для оценки чувствительности системы.

## Сценарий 7: Отказоустойчивость — недоступность control plane

**Цель:** подтвердить, что data plane (sidecar-прокси) продолжает обслуживать трафик при временной недоступности control plane.

**Шаги:**

1. Убедиться, что mesh работает нормально (запросы проходят)
2. Масштабировать control plane до 0 реплик:
   ```bash
   kubectl -n mesh scale deployment mesh-control-plane --replicas=0
   ```
3. Продолжать отправлять запросы через API Gateway
4. Через 2–3 минуты вернуть control plane:
   ```bash
   kubectl -n mesh scale deployment mesh-control-plane --replicas=1
   ```

**Ожидаемый результат:** запросы продолжают обрабатываться по последней кэшированной конфигурации. В логах sidecar появляются WARN о невозможности обновить конфигурацию. После возврата control plane — синхронизация восстанавливается автоматически.

**Что демонстрирует:** принцип graceful degradation — data plane не зависит от доступности control plane для обработки текущего трафика. Это ключевое архитектурное свойство, отличающее service mesh от централизованных прокси.

## Сценарий 8: Поведение при отсутствии трафика

**Цель:** проверить, как evaluator обрабатывает ситуацию, когда canary запущен, но трафика через mesh нет (или его недостаточно).

**Шаги:**

1. Запустить canary
2. Не отправлять запросы через API Gateway
3. Наблюдать логи control plane и `GET /canary/status`

**Ожидаемый результат:** evaluator каждые 30 секунд логирует "insufficient data for inventory-service, skipping". Canary остаётся в статусе `IN_PROGRESS`, вес не меняется. Система не принимает решений при недостаточных данных — ни promote, ни rollback.

**Что демонстрирует:** защита от ложных решений при отсутствии статистически значимого объёма метрик. Evaluator корректно отличает «нет ошибок» от «нет данных».

---

## Сценарий 9: Попытка запуска второго canary

**Цель:** подтвердить ограничение прототипа — одновременно допускается только один активный canary.

**Шаги:**

1. Запустить canary для inventory-service
2. Попытаться запустить ещё один canary (повторный `POST /canary/start`)

**Ожидаемый результат:** HTTP 409 Conflict с сообщением "Canary already in progress for service: inventory-service".

**Что демонстрирует:** защита от конфликтующих канареечных релизов. В реальных системах может поддерживаться несколько параллельных canary для разных сервисов, но данный прототип ограничен одним.

---

## Сценарий 10: Влияние канареечного релиза на распределение нагрузки между подами

**Цель:** проверить, что при канареечном релизе трафик корректно распределяется между stable-подами и canary-подом в соответствии с заданными весами.

**Шаги:**

1. Исходное состояние: 2 stable пода inventory-service
2. Запустить canary (1 canary под)
3. Отправить 100 запросов
4. Подсчитать распределение по version в ответах

**Ожидаемый результат:** ~90 ответов с version=v1 (stable), ~10 с version=v2 (canary). Допустимое отклонение ±5% из-за стохастической природы weighted random.

**Дополнительная проверка:** панель "RPS by pod" в Grafana показывает, что трафик к stable-подам распределён равномерно между обоими подами (~45% каждому), а canary-под получает свои ~10%.
